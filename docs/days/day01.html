Day 1: Roadmap, mindset, and the journey of one request

Videos 1 & 2 ~30 min read Source lessons: 1. Roadmap for backend from first principles · 2. Walk the path of a true backend engineer

What Sriniously teaches in these videos

  • Backend engineering is not "learn Express/Django/Spring". Frameworks are the last layer, not the first. The course walks the stack from the bottom: HTTP, routing, serialization, auth, validation, architecture, databases, caching, queues, search, errors, config, observability, shutdown, security, scaling, concurrency, storage, real-time, testing, 12-factor, OpenAPI, webhooks, DevOps.
  • "First principles" means: for every tool, know the problem it solves, what it does underneath, and what you would do without it. Then any framework in any language becomes a thin skin over things you already understand.
  • The mindset of a real backend engineer: read the specification, not the blog post. Build the thing once by hand before you use the library. Ask "what happens on the wire / in the kernel / in memory" until you hit something you can't go below.
  • Language is a detail. He uses JavaScript/TypeScript; we use C and C++ precisely because they hide nothing. Every syscall, every byte, every allocation is in front of you.
  • The path is long on purpose. Each topic builds on the previous one. Skipping ahead leaves holes that show up at 3 a.m. during an outage.

The problem before "first principles"

Most people learn backend development backwards. They start with a framework tutorial. On day one they have a working server, a database, and a login page. On day thirty they have a product. On day ninety the product is slow under load and nobody on the team can say why.

What happened is that the framework did a hundred things for them, silently. It parsed the HTTP request, decoded the URL, matched a route, parsed JSON, checked a session cookie, opened a database connection from a pool, serialized a response, set headers, and closed the socket. They never saw any of it. So when one of those hundred things goes wrong, they are blind. They can only google the error message and try the first answer.

This is the problem first principles solves. Not "know everything", but know what is underneath everything you use. When the framework fails, you can reason one layer down. When the layer below that fails, one more. You stop at the kernel, and the kernel is very well documented.

A concrete example. A request to /api/orders takes 4 seconds. The framework engineer sees "slow endpoint". The first-principles engineer asks, in order: Is it DNS? TCP connect? TLS handshake? Server accept queue full? Request parsing? Route handler? Database query? Database connection pool exhausted? Serialization of a huge response? Slow client reading the response? Each question is a layer, and each layer has a tool to measure it. By the end of this course, you will have that list in your head and know how each layer works.

When you need this mindset, and when you don't

You do not need to hand-write an HTTP parser to ship a weekend project. Frameworks exist because the problems are solved; reinventing them in production is usually a mistake. Use the library. Use the framework.

You do need to have hand-written one once, so that you know:

  • what the library is doing for you, and therefore what it can get wrong;
  • what the limits are (why a 2 GB upload breaks it, why 10 000 idle connections exhaust it);
  • how to read its source code or its logs when it misbehaves;
  • how to pick between two libraries, because you know the trade-off they each made.

The rule of thumb for this course: build it by hand once to understand it, then use the real tool in production. Every "See it in C" section is the "once". Every "How real tools do it" section is the "then".

When is it over-engineering? If you are writing your own HTTP server for a company product in 2026 without a very specific reason (embedded device, extreme performance, no dependency policy), that is over-engineering. The understanding is the goal, not the artifact.

Layer by layer

DNS (Domain Name System). Humans use names, the network uses numbers. The browser (really, the OS resolver library) asks: what IP address is example.com? It checks a local file first (/etc/hosts), then a local cache, then sends a small UDP packet to a resolver (your router, your ISP, or 1.1.1.1). The answer comes with a TTL (time to live) in seconds, and is cached for that long. From C, this whole dance is one call: getaddrinfo(). Day 1's program uses it.

TCP (Transmission Control Protocol). IP delivers packets with no guarantee of order or arrival. TCP builds a reliable, ordered byte stream on top. Before any data moves, client and server do a three-way handshake: SYN, SYN+ACK, ACK. That costs one full round trip (RTT) before you send a single byte of HTTP. On the server side, the kernel completes this handshake without your process being involved; your process only sees the finished connection when it calls accept(). On the client, it is socket() then connect().

Sockets. A socket is the kernel object that represents one endpoint of a connection. To your program it is just a file descriptor (an int). You send() bytes into it and recv() bytes out of it. The kernel handles packets, retransmission, ordering, flow control. This is why a backend is "just a process": it reads from an fd and writes to an fd.

HTTP (HyperText Transfer Protocol). HTTP/1.1 is plain text. A request is a request line (GET /orders HTTP/1.1), then header lines (Name: value), then an empty line, then an optional body. A response is a status line (HTTP/1.1 200 OK), headers, empty line, body. Lines end in \r\n. That's it. The entire web runs on this. Day 3 goes deep.

Your process. Everything between recv() and send() is "the backend": parsing, routing, authentication, validation, business logic, talking to a database (which is itself another socket to another process), serializing the answer. Days 3 to 18 are this box.

Back out. The response bytes go into the socket, the kernel splits them into TCP segments, the client's kernel reassembles them, the browser parses the same text format in reverse.

Where the time goes

Typical numbers for one request from a laptop to a server in the same country. Rough, but the orders of magnitude matter:

See it in C

This program does steps 1 to 4 and 9 of the diagram by hand: DNS lookup, TCP connect, send a raw HTTP request, print the raw response. No libraries except the C standard library and the POSIX socket API. Run it as ./http_get example.com /.

http_get.cC17 · POSIX
// http_get.c — the whole journey of one request, by hand.
// DNS lookup -> TCP connect -> send HTTP request -> read HTTP response.
#define _POSIX_C_SOURCE 200112L
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>        /* close */
#include <netdb.h>         /* getaddrinfo */
#include <sys/socket.h>    /* socket, connect, send, recv */
#include <arpa/inet.h>     /* inet_ntop */

int main(int argc, char **argv) {
    const char *host = argc > 1 ? argv[1] : "example.com";
    const char *path = argc > 2 ? argv[2] : "/";

    /* 1. DNS: turn a name into addresses.
       getaddrinfo asks the system resolver, which checks /etc/hosts,
       then the DNS servers listed in /etc/resolv.conf.  It can return
       several addresses (IPv4 and IPv6); we get a linked list. */
    struct addrinfo hints = {0};
    hints.ai_family   = AF_UNSPEC;    /* IPv4 or IPv6, we don't care   */
    hints.ai_socktype = SOCK_STREAM;  /* TCP (a stream), not UDP       */
    struct addrinfo *res = NULL;
    int rc = getaddrinfo(host, "80", &hints, &res);
    if (rc != 0) {
        fprintf(stderr, "DNS failed: %s\n", gai_strerror(rc));
        return 1;
    }

    /* 2. TCP: try each address until connect() succeeds.
       connect() is where the three-way handshake happens.  It blocks
       until the handshake completes or fails (refused, timeout). */
    int fd = -1;
    for (struct addrinfo *p = res; p; p = p->ai_next) {
        char ip[INET6_ADDRSTRLEN];
        void *addr = (p->ai_family == AF_INET)
            ? (void *)&((struct sockaddr_in  *)p->ai_addr)->sin_addr
            : (void *)&((struct sockaddr_in6 *)p->ai_addr)->sin6_addr;
        inet_ntop(p->ai_family, addr, ip, sizeof ip);
        printf("trying %s ...\n", ip);

        fd = socket(p->ai_family, p->ai_socktype, p->ai_protocol);
        if (fd < 0) continue;
        if (connect(fd, p->ai_addr, p->ai_addrlen) == 0) break;  /* SYN, SYN+ACK, ACK done */
        close(fd);
        fd = -1;
    }
    freeaddrinfo(res);  /* the list was malloc'd by the resolver; give it back */
    if (fd < 0) { perror("connect"); return 1; }

    /* 3. HTTP: it is just text.  Lines end in \r\n; an empty line ends the headers.
       "Host" is mandatory in HTTP/1.1 because one IP can serve many sites.
       "Connection: close" asks the server to hang up after one response,
       which makes "read until EOF" a correct way to find the end. */
    char req[512];
    int n = snprintf(req, sizeof req,
        "GET %s HTTP/1.1\r\n"
        "Host: %s\r\n"
        "Connection: close\r\n"
        "\r\n", path, host);

    /* send() may write FEWER bytes than asked (socket buffer full).
       A loop until everything is out is the only correct way. */
    size_t sent = 0;
    while (sent < (size_t)n) {
        ssize_t w = send(fd, req + sent, (size_t)n - sent, 0);
        if (w < 0) { perror("send"); close(fd); return 1; }
        sent += (size_t)w;
    }

    /* 4. Read the reply until the server closes the connection (recv returns 0).
       Each recv() returns whatever has arrived so far: maybe 1 byte, maybe 4096.
       Never assume one recv() == one message.  That assumption is bug #1 in
       every hand-written network program. */
    char buf[4096];
    ssize_t r;
    while ((r = recv(fd, buf, sizeof buf, 0)) > 0)
        fwrite(buf, 1, (size_t)r, stdout);
    if (r < 0) perror("recv");

    close(fd);  /* sends FIN; the kernel finishes the TCP teardown for us */
    return 0;
}

What to notice. There are exactly six kernel calls that matter: getaddrinfo (which internally does the UDP DNS exchange), socket, connect, send, recv, close. Everything else is string formatting. When you run it you will see the server's raw response, status line and headers included. That text is what every HTTP library in every language is parsing for you.

The two loops are not optional. The send loop handles partial writes. The recv loop handles partial reads. TCP is a byte stream with no message boundaries, so the kernel is free to hand you data in any chunking it likes. Programs that do a single recv and assume they got "the response" work on localhost and fail in production. Day 3 builds on this when we parse HTTP incrementally.

See it in modern C++

The C version has a resource-leak trap on every early return: forget one close(fd) and the descriptor leaks. The addrinfo list has the same problem. C++ fixes this with RAII (Resource Acquisition Is Initialization): the resource is owned by an object, and the object's destructor releases it, on every exit path, including exceptions. The logic is identical; the safety is structural.

http_get.cppC++20 · POSIX
// http_get.cpp — same journey, with every resource owned by an object.
#include <cstdio>
#include <iostream>
#include <memory>
#include <optional>
#include <string>
#include <string_view>
#include <netdb.h>
#include <unistd.h>
#include <sys/socket.h>

// A socket that closes itself.  Move-only: two owners would mean two close() calls.
class Socket {
    int fd_ = -1;
public:
    Socket() = default;
    explicit Socket(int fd) : fd_(fd) {}
    ~Socket() { if (fd_ >= 0) ::close(fd_); }

    Socket(const Socket&)            = delete;
    Socket& operator=(const Socket&) = delete;
    Socket(Socket&& o) noexcept : fd_(o.fd_) { o.fd_ = -1; }
    Socket& operator=(Socket&& o) noexcept {
        if (this != &o) { if (fd_ >= 0) ::close(fd_); fd_ = o.fd_; o.fd_ = -1; }
        return *this;
    }

    int  get()   const { return fd_; }
    bool valid() const { return fd_ >= 0; }
};

// getaddrinfo's list, freed automatically by freeaddrinfo.
using AddrList = std::unique_ptr<addrinfo, decltype(&::freeaddrinfo)>;

std::optional<AddrList> resolve(const std::string& host, const char* port) {
    addrinfo hints{};
    hints.ai_family   = AF_UNSPEC;
    hints.ai_socktype = SOCK_STREAM;
    addrinfo* raw = nullptr;
    if (int rc = ::getaddrinfo(host.c_str(), port, &hints, &raw); rc != 0) {
        std::cerr << "DNS failed: " << ::gai_strerror(rc) << '\n';
        return std::nullopt;
    }
    return AddrList(raw, &::freeaddrinfo);
}

std::optional<Socket> connect_any(const addrinfo* list) {
    for (const addrinfo* p = list; p; p = p->ai_next) {
        Socket s(::socket(p->ai_family, p->ai_socktype, p->ai_protocol));
        if (!s.valid()) continue;
        if (::connect(s.get(), p->ai_addr, p->ai_addrlen) == 0) return s;  // moved out
        // on failure `s` is destroyed here and close() runs for us
    }
    return std::nullopt;
}

// string_view lets us shrink the "still to send" window without copying.
bool send_all(const Socket& s, std::string_view data) {
    while (!data.empty()) {
        ssize_t w = ::send(s.get(), data.data(), data.size(), 0);
        if (w < 0) return false;
        data.remove_prefix(static_cast<size_t>(w));
    }
    return true;
}

int main(int argc, char** argv) {
    std::string host = argc > 1 ? argv[1] : "example.com";
    std::string path = argc > 2 ? argv[2] : "/";

    auto addrs = resolve(host, "80");
    if (!addrs) return 1;

    auto sock = connect_any(addrs->get());
    if (!sock) { std::perror("connect"); return 1; }

    std::string req = "GET " + path + " HTTP/1.1\r\n"
                      "Host: " + host + "\r\n"
                      "Connection: close\r\n\r\n";
    if (!send_all(*sock, req)) { std::perror("send"); return 1; }

    char buf[4096];
    for (ssize_t r; (r = ::recv(sock->get(), buf, sizeof buf, 0)) > 0;)
        std::cout.write(buf, r);

    return 0;  // sock and addrs clean themselves up, in reverse order of creation
}

Why this is better than the C version. Count the close() calls in main: zero. Count the early returns: three. In C each of those returns would need its own cleanup, and the fourth one you add next month is the one you forget. Here, Socket's destructor and unique_ptr's deleter run automatically. std::optional makes "this might fail" visible in the function signature instead of a magic -1. std::string_view gives send_all a window onto the data that it can shrink without copying a byte.

Where a real library fits. In production you would use libcurl (C) or cpp-httplib / Boost.Beast (C++). Internally, libcurl does exactly this: getaddrinfo (with its own cache and parallel IPv4/IPv6 "happy eyeballs" connect), a non-blocking connect with a timeout, the same send/recv loops, plus HTTP parsing, redirects, TLS, and connection reuse. Knowing this program means you can read libcurl's verbose output (curl -v) and understand every line.

Real-world use cases

Debugging "the API is slow"

With the request journey in your head, you measure each layer. dig example.com for DNS. curl -w '%{time_connect} %{time_starttransfer} %{time_total}' for connect vs server think-time vs transfer. If connect is 200 ms, it's the network or a full accept queue. If starttransfer is 3 s, it's inside your process (usually the database). You stop guessing.

Picking a tech stack

Should this service use HTTP/1.1, HTTP/2, gRPC, or WebSockets? That question is unanswerable from a framework's docs and trivial from first principles: how many round trips can you afford, do you need multiplexing, is the payload binary, does the server need to push? Days 3 and 24 give you the vocabulary.

Reading other people's code

Every web framework, in any language, has the same shape underneath: a listening socket, an accept loop, a parser, a router, a chain of middlewares, a handler, a serializer. Once you have built each one in C, you can open Express, Django, Spring, Actix or Gin and find each piece in minutes.

How real tools do it

Nginx is a C program whose core is: open listening sockets, run an event loop per worker process, accept connections, parse HTTP with a hand-written state machine, proxy to an upstream over another socket. Postgres is a C program that listens on port 5432, forks one process per client connection, and reads a binary protocol from the socket. Redis is a C program with a single-threaded event loop reading a text protocol (RESP) from sockets. Every one of them is "a process that reads from file descriptors and writes to file descriptors". You will read parts of each one in this course.

What if it's missing?

If you skip first principles entirely

You can still ship. Many people do. The cost arrives later, as a specific set of symptoms: you copy configuration you don't understand (keepAliveTimeout, poolSize, backlog) and change it by trial and error; you cannot tell whether a bug is in your code, the framework, the kernel, or the network; you over-provision servers because you can't find the bottleneck; and you cannot evaluate a new tool except by its popularity. None of these are fatal on a small project. All of them are expensive on a large one.

If you do it wrong

The opposite failure is only first principles: rewriting everything from scratch, refusing libraries, treating every dependency as a weakness. That produces slow, buggy, half-finished infrastructure. The course's rule stands: build it once to understand it, then use the production tool. Understanding is the asset, not the hand-written code.

If a layer of the journey is not available

  • No DNS (resolver down, or an internal network without one). Fall back to IP addresses in configuration, /etc/hosts, or a service-discovery system (Consul, Kubernetes DNS). Trade-off: hard-coded IPs break on every redeploy. getaddrinfo accepts a literal IP, so the C program above works unchanged with ./http_get 93.184.216.34 / (though the Host header still needs the name).
  • No TCP (you must use UDP, e.g. for games, DNS itself, or QUIC). You lose ordering, reliability and flow control and must rebuild whichever of those you need. HTTP/3 does exactly this over QUIC over UDP. Day 3 and Day 24 touch this.
  • No HTTP (a custom binary protocol over raw TCP). Perfectly valid, and how Postgres, Redis, and most databases work. You give up every HTTP tool (browsers, curl, proxies, caches) and must write your own framing. Day 5 covers framing and serialization.
  • No network at all (two processes on one machine). Use a Unix domain socket: the same socket()/connect()/accept() calls, but no IP, no TCP, no handshake, much faster. Postgres defaults to one. Same code shape, different address family.

Common mistakes & gotchas

  • Assuming one recv() returns one message. TCP has no messages, only bytes. Always loop and always have a way to find the end (Content-Length, a delimiter, or EOF).
  • Ignoring partial send(). On a slow link or full buffer, send returns fewer bytes than asked. Without the loop, the tail of your request silently vanishes.
  • Forgetting freeaddrinfo / close on error paths. Each leaked fd is one fewer connection your process can make. The limit is often 1024. Use RAII in C++; in C, use a single cleanup label with goto.
  • Byte order. Ports and IPv4 addresses on the wire are big-endian. htons/htonl convert. Forgetting them connects to port 36895 instead of 8080 (that's 0x1F90 byte-swapped).
  • Missing Host header. Most servers return 400 without it, because one IP hosts many names.
  • Blocking forever. connect and recv block with no timeout by default. A dead server hangs your program. Days 14 and 19 add timeouts and non-blocking I/O.
  • Treating DNS as free. An uncached lookup is a network round trip. Hot loops that call getaddrinfo per request are a classic hidden latency source.

Think about it

1. Run http_get against three different sites. Which headers appear in every response? Which are specific to one server?

You will almost always see Content-Type, Content-Length (or Transfer-Encoding: chunked), Date, and often Server. Site-specific ones include cache headers, security headers (Strict-Transport-Security), and cookies. The point: the format is fixed, the vocabulary is open. Day 3 covers the important ones.

2. What would happen if you removed the Connection: close header?

HTTP/1.1 defaults to keep-alive, so the server would send the response and then wait for your next request. Your recv loop waits for EOF, which never comes, so the program hangs after printing the response, until the server's idle timeout (often 5 to 60 s) closes it. To handle keep-alive correctly you must parse Content-Length and stop reading after that many body bytes. That is Day 3's parser.

3. What would happen if send() returned 0 or you sent the request one byte at a time?

It would work. TCP is a stream; the server's parser reassembles bytes regardless of how they were chunked on the way in. This is also why a server can never assume it received the whole request in one recv: the client may be slow, or malicious (the "Slowloris" attack sends one byte every few seconds to tie up connections, Day 18).

4. Change the C++ Socket to allow copying. What exactly breaks?

Two Socket objects hold the same fd. When the first is destroyed it calls close(fd). The kernel may then reuse that fd number for a new file or connection. The second object, still holding the old number, later closes or writes to someone else's descriptor. This is a real bug class in C servers; deleting the copy constructor makes it a compile error instead.

5. (Harder) Modify http_get.c to print how long the DNS step and the connect step each took, using clock_gettime(CLOCK_MONOTONIC, ...). Run it twice in a row. Why is the second DNS time near zero?

The system resolver (or a local caching daemon such as systemd-resolved) cached the answer for its TTL. The connect time does not change, because every run performs a new three-way handshake. This is the first measurement in the "where does the time go" table, made by you.

Quiz

1. Why does an HTTP request need at least one full round trip before any data is sent?

TCP's three-way handshake (SYN, SYN+ACK, ACK) must complete before the stream exists. Only then can the client send the request bytes. TLS adds one or two more. This is why connection reuse matters so much.

2. A backend process receives a request. Which kernel call hands it the connection, and what does that call return?

accept(). It returns a new file descriptor for that one connection; the listening socket's fd is unchanged and keeps accepting others.

3. When should you use a framework rather than hand-written socket code?

Almost always in production. Hand-writing is for understanding (and rare cases like embedded or extreme performance). The goal of writing it once is to be able to debug, configure and choose the framework well.

4. Why is "read until recv returns 0" a correct way to find the end of the response in today's program, and when would it be wrong?

Because we sent Connection: close, the server closes after one response, and 0 means EOF. With keep-alive the connection stays open, so you must use Content-Length or chunked encoding to find the end.

5. Name the six syscalls a TCP client needs, in order.

getaddrinfo (DNS), socket, connect, send, recv, close.

Summary & key terms

A backend is a process that reads bytes from a socket, does work, and writes bytes back. Getting those bytes there involves DNS (name to address), TCP (reliable stream with a handshake), and HTTP (a text format with a request line, headers, blank line, body). First principles means knowing what each layer does so that, when the framework hides it and it breaks, you can reason one layer down. The course builds every layer by hand once, in C and C++, then shows how the real tools do it and what to do when they're not there.
