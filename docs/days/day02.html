Day 2: What a backend is, how it works, and why it exists

Videos 3 & 4 ~35 min read Source lessons: 3. What is a Backend, how do they work and why do we need them? · 4. Benefits of learning backend engineering from first principles

What Sriniously teaches in these videos

  • A backend is the part of a system the user never sees: it holds the data, enforces the rules, and talks to other systems. The frontend is a view onto it.
  • Backends exist because of three things a client cannot provide: a shared source of truth (many users, one dataset), trust (the client is in the user's hands and can be modified), and capability (secrets, heavy computation, access to other systems).
  • Mechanically, a backend is a long-running program that waits for requests, does work, and replies. Request in, response out. Everything else is detail.
  • Learning it from first principles pays off three ways: you can debug anything because you know the layers; you are language- and framework-independent; and you can design systems rather than assemble them.

The problem before backends existed

Imagine a to-do app with no backend. It runs entirely on your laptop, stores its list in a file. It works perfectly, until you want to see the list on your phone. Now the data lives in two places and must be synchronized. Add a second user who shares the list, and you have three copies, conflicts, and no answer to "which one is right?"

Now imagine the app lets you buy things. The price is computed on your laptop. A user opens the developer tools, changes price = 0.01, and clicks buy. Nothing stops them, because every line of code the client runs is under the user's control.

Finally imagine the app needs to send an email. That requires credentials for an email service. If the credentials are in the client, every user has them.

Those three problems have one solution: put a program somewhere the user cannot reach, give it the single copy of the data, make it enforce the rules, and give it the secrets. Clients send it requests; it decides what happens. That program is the backend. The network between them is the trust boundary.

The one-line definition. A backend is a process you control, reachable over a network, that owns the truth. "You control" gives trust. "Over a network" gives sharing. "Owns the truth" gives consistency.

When you need a backend, and when you don't

You need one when any of these is true:

  • More than one device or user must see the same data.
  • Some rule must hold even if the user tampers with the client (prices, permissions, rate limits, uniqueness of usernames).
  • Something must happen when no client is running: scheduled jobs, receiving webhooks, sending notifications.
  • You hold a secret the user must not have: API keys, payment credentials, other users' data.
  • The computation is too heavy or the data too large for the client.

You do not need one when none of those hold. A calculator, a note-taking app for one device, a static documentation site, a game with no leaderboard: these are better without a backend. No server to pay for, no outages, no data breach possible, works offline. Many products add a backend on day one out of habit and then carry its cost forever. The honest question is "which of the five reasons applies?" If the answer is none, don't build one yet.

There is a middle ground, covered in the "what if" section: a static site with a third-party API for the one thing that needs a server, or local-first apps that sync.

How a backend works, from the OS up

Strip away every framework and a backend is this: a process that asks the kernel for a listening socket, then loops forever doing accept, recv, work, send, close. Here are the four parts and what each one actually does.

The client

Any program that opens a TCP connection and speaks the protocol: a browser, a mobile app, curl, another backend. From the server's point of view they are identical: a stream of bytes arriving on a file descriptor. The server cannot tell a browser from a Python script, which is exactly why it must not trust anything the client says (Day 7).

The network

Day 1 covered DNS and TCP. The one new idea today: on the server side, the kernel does the handshake on its own. Your process never sees SYN packets. It calls listen() once, and from then on the kernel completes handshakes in the background and parks finished connections in a queue (the accept queue or backlog). Your process drains that queue with accept(). If the queue fills because your process is too slow, new clients see connection timeouts or resets even though your process is "running". This is the first scaling limit you will meet, and it is set by one integer argument to listen().

The process

Four states, forever:

          socket()  ->  bind(:8080)  ->  listen(backlog)        [done once at startup]
                                            |
                 +--------------------------+
                 |
                 v
     +----> accept()  --- BLOCKS until the kernel has a completed connection
     |         |           (process is asleep here; uses 0% CPU)
     |         v
     |      recv(conn_fd) --- BLOCKS until bytes arrive; may return a partial request
     |         |
     |         v
     |      parse -> route -> handler -> (maybe talk to a DB over another socket)
     |         |
     |         v
     |      send(conn_fd, response)
     |         |
     |         v
     +----- close(conn_fd)      (listening socket stays open)

The word blocks is the key to everything that follows in this course. A blocking call puts the process to sleep until the kernel has something for it. That is efficient (no busy-waiting) but it means this process can serve exactly one client at a time. While it is in recv waiting for a slow client, every other client sits in the accept queue. Day 19 to 21 are entirely about escaping this: threads, processes, non-blocking sockets, epoll. Today we accept the limitation to see the shape clearly.

The OS

The kernel owns every socket. It holds the receive buffer where incoming bytes wait until you recv them, the send buffer where your outgoing bytes wait to be transmitted, the accept queue, the TCP state machine, retransmission timers, and the file-descriptor table that maps your little integers to all of this. When people say a server "handles 10 000 connections", they mean the kernel holds 10 000 of these structures and the process has 10 000 fds. Each one costs a few kilobytes of kernel memory. This is where the per-connection limits come from (ulimit -n, Day 19).

Why the browser understands the reply

Because the server writes valid HTTP: a status line, headers, a blank line, a body. The browser doesn't know or care that the server is 60 lines of C. The protocol is the contract. Replace the C with Go, Java, or a 20 MB framework and the bytes on the wire are the same. That is what "language is a detail" means.

See it in C

A complete backend. It listens on port 8080, accepts one connection at a time, prints the request line, and returns an HTML page. Run it, then open http://localhost:8080 in a browser, or run curl -v localhost:8080 to see both directions as text.

hello_server.cC17 · POSIX
// hello_server.c — a backend in under 70 lines: a process that waits in accept().
#define _POSIX_C_SOURCE 200112L
#include <stdio.h>
#include <string.h>
#include <unistd.h>        /* close */
#include <netinet/in.h>    /* sockaddr_in, htons, INADDR_ANY */
#include <sys/socket.h>    /* socket, bind, listen, accept, recv, send */

int main(void) {
    /* 1. Ask the kernel for a TCP socket.  It is an endpoint with no address yet. */
    int listen_fd = socket(AF_INET, SOCK_STREAM, 0);
    if (listen_fd < 0) { perror("socket"); return 1; }

    /* Allow immediate restart.  Without this, after you stop the server the port
       stays reserved for ~60 s (TCP TIME_WAIT) and bind() fails with
       "Address already in use". */
    int yes = 1;
    setsockopt(listen_fd, SOL_SOCKET, SO_REUSEADDR, &yes, sizeof yes);

    /* 2. bind: attach the socket to an address.  0.0.0.0 means "every interface
       on this machine".  Port and address are in NETWORK byte order (big-endian),
       hence htons/htonl.  Forget them and you listen on port 36895. */
    struct sockaddr_in addr = {0};
    addr.sin_family      = AF_INET;
    addr.sin_addr.s_addr = htonl(INADDR_ANY);
    addr.sin_port        = htons(8080);
    if (bind(listen_fd, (struct sockaddr *)&addr, sizeof addr) < 0) {
        perror("bind"); return 1;
    }

    /* 3. listen: from now on the KERNEL completes TCP handshakes for us and queues
       finished connections.  16 is the queue length (backlog).  If it fills,
       new clients are refused or time out even though we are "running". */
    if (listen(listen_fd, 16) < 0) { perror("listen"); return 1; }
    printf("listening on http://localhost:8080\n");

    for (;;) {
        /* 4. accept: BLOCK here until a connection is ready.  The process sleeps;
           it uses no CPU.  Returns a NEW fd that represents this one client.
           The listening fd is untouched and keeps queueing other clients. */
        struct sockaddr_in peer;
        socklen_t peer_len = sizeof peer;
        int conn_fd = accept(listen_fd, (struct sockaddr *)&peer, &peer_len);
        if (conn_fd < 0) { perror("accept"); continue; }

        /* 5. recv: read whatever the client has sent so far.  A browser sends an
           HTTP request as plain text.  One recv() may return only part of it;
           we tolerate that here because we only look at the first line.
           (Day 3 builds a parser that handles arbitrary chunking.) */
        char buf[4096];
        ssize_t n = recv(conn_fd, buf, sizeof buf - 1, 0);
        if (n > 0) {
            buf[n] = '\0';
            char *eol = strstr(buf, "\r\n");     /* end of the request line */
            if (eol) *eol = '\0';
            printf("request: %s\n", buf);         /* e.g. "GET / HTTP/1.1" */
        }

        /* 6. send: write a valid HTTP/1.1 response.
           Status line, headers, blank line, body.  Content-Length tells the
           browser exactly how many body bytes to expect, so it knows when the
           page is complete. */
        const char *body = "<h1>Hello from a C process</h1>";
        char resp[512];
        int resp_len = snprintf(resp, sizeof resp,
            "HTTP/1.1 200 OK\r\n"
            "Content-Type: text/html\r\n"
            "Content-Length: %zu\r\n"
            "Connection: close\r\n"
            "\r\n"
            "%s", strlen(body), body);
        send(conn_fd, resp, (size_t)resp_len, 0);

        /* 7. close THIS connection.  The browser sees EOF and knows we are done.
           The listening socket stays open; we loop back to accept(). */
        close(conn_fd);
    }
}

Trace one request through it. You start the program: steps 1 to 3 run, and it prints "listening". The process is now asleep inside accept(). You open the browser. The browser's kernel sends SYN; your kernel replies SYN+ACK; the browser's kernel sends ACK. Your process is still asleep. The kernel puts the finished connection in the accept queue and wakes your process. accept() returns, say, fd 4. The browser's request bytes have probably already arrived in the kernel's receive buffer for fd 4, so recv() returns immediately with "GET / HTTP/1.1\r\nHost: localhost:8080\r\n...". You print the first line, write the response into the socket, close fd 4. The browser renders the HTML. Your process loops back to accept() and sleeps. Total: seven syscalls and one page served.

Try this. Open the page twice quickly, or in two tabs. It works, because each request is short and the loop is fast. Now add sleep(5); before send and open two tabs. The second one waits 10 seconds. That is the one-client-at-a-time limit made visible. Hold on to that feeling; Day 19 fixes it.

See it in modern C++

Same syscalls, same behaviour on the wire. The difference is that every file descriptor is owned by an object, so the continue in the accept loop, an early return, or a thrown exception can never leak a connection. We also build the response with std::string instead of a fixed buffer that could silently truncate a long body.

hello_server.cppC++20 · POSIX
// hello_server.cpp — the same server, with every resource owned by an object.
#include <cstdint>
#include <cstdio>
#include <iostream>
#include <optional>
#include <string>
#include <string_view>
#include <unistd.h>
#include <netinet/in.h>
#include <sys/socket.h>

// Move-only owner of a file descriptor.  Destructor closes it.
class Socket {
    int fd_ = -1;
public:
    Socket() = default;
    explicit Socket(int fd) : fd_(fd) {}
    ~Socket() { if (fd_ >= 0) ::close(fd_); }
    Socket(const Socket&)            = delete;
    Socket& operator=(const Socket&) = delete;
    Socket(Socket&& o) noexcept : fd_(o.fd_) { o.fd_ = -1; }
    Socket& operator=(Socket&& o) noexcept {
        if (this != &o) { if (fd_ >= 0) ::close(fd_); fd_ = o.fd_; o.fd_ = -1; }
        return *this;
    }
    int  get()   const { return fd_; }
    bool valid() const { return fd_ >= 0; }
};

// socket + setsockopt + bind + listen, or nothing.  The caller cannot forget a step.
std::optional<Socket> make_listener(std::uint16_t port, int backlog = 16) {
    Socket s(::socket(AF_INET, SOCK_STREAM, 0));
    if (!s.valid()) return std::nullopt;

    int yes = 1;
    ::setsockopt(s.get(), SOL_SOCKET, SO_REUSEADDR, &yes, sizeof yes);

    sockaddr_in addr{};
    addr.sin_family      = AF_INET;
    addr.sin_addr.s_addr = htonl(INADDR_ANY);
    addr.sin_port        = htons(port);
    if (::bind(s.get(), reinterpret_cast<sockaddr*>(&addr), sizeof addr) < 0) return std::nullopt;
    if (::listen(s.get(), backlog) < 0) return std::nullopt;
    return s;   // moved out; on any failure above, s is destroyed and closed
}

// Build a complete HTTP/1.1 response.  std::string grows, so no truncation risk.
std::string http_response(std::string_view body, std::string_view type = "text/html") {
    std::string r;
    r.reserve(128 + body.size());
    r += "HTTP/1.1 200 OK\r\n";
    r += "Content-Type: "; r += type; r += "\r\n";
    r += "Content-Length: " + std::to_string(body.size()) + "\r\n";
    r += "Connection: close\r\n";
    r += "\r\n";
    r += body;
    return r;
}

int main() {
    auto listener = make_listener(8080);
    if (!listener) { std::perror("listen"); return 1; }
    std::cout << "listening on http://localhost:8080\n";

    for (;;) {
        // One Socket per connection.  Its lifetime IS the connection's lifetime.
        Socket conn(::accept(listener->get(), nullptr, nullptr));
        if (!conn.valid()) { std::perror("accept"); continue; }   // nothing to leak

        char buf[4096];
        ssize_t n = ::recv(conn.get(), buf, sizeof buf, 0);
        if (n > 0) {
            std::string_view req(buf, static_cast<std::size_t>(n));
            std::cout << "request: " << req.substr(0, req.find("\r\n")) << '\n';
        }

        std::string resp = http_response("<h1>Hello from a C++ process</h1>");
        ::send(conn.get(), resp.data(), resp.size(), 0);

        // `conn` goes out of scope here: close() is guaranteed, every iteration.
    }
}

What changed and why it matters. make_listener bundles the four startup steps so they cannot be done in the wrong order or half-done. std::optional<Socket> makes failure part of the type. The per-connection Socket conn is destroyed at the end of each loop iteration, so close happens even on the continue, even if a future version throws. std::string_view gives us find and substr on the raw buffer without copying and without needing a NUL terminator, which removes the buf[n] = '\0' trick and the off-by-one it invites.

Where a real library fits. cpp-httplib (header-only C++), Boost.Beast, or Drogon do what this file does, plus: a thread pool so many clients are served at once, a full HTTP parser, keep-alive, routing, TLS. Open cpp-httplib's Server::listen_internal and you will find this exact loop: accept, hand the fd to a worker, worker calls recv, parses, calls your handler, calls send, closes. Nginx's ngx_event_accept is the same idea with non-blocking sockets. The shape never changes.

Real-world use cases

An e-commerce checkout

The client shows a cart and a "pay" button. The backend recomputes the total from the database prices (never trusting the client's number), checks stock, charges the card using a secret API key the client never sees, writes the order, and replies with an order ID. All five reasons for a backend apply at once: shared data, trust, secrets, something must happen server-side, and other systems are involved.

A chat app

Messages must reach other users' devices, so a process somewhere must hold them and fan them out. The backend's accept loop is handling thousands of long-lived connections at once, which is the exact problem today's one-at-a-time server cannot solve. Day 21 and 24 build this.

A mobile game leaderboard

The game runs on the phone with no backend, until scores must be compared across players. Then a tiny backend appears whose only job is "accept a score, verify it looks plausible, store it, return the top 100". Its trust role is the important one: scores submitted by a modified client must be caught here, because they cannot be caught anywhere else.

Internal services talking to each other

In a large system, most clients of a backend are other backends. The "orders" service calls the "inventory" service. Same accept/recv/send, same HTTP, but the trust boundary is different: inside a network you control, you may trust the caller's identity but must still validate its data. Day 8 and Day 18 return to this.

How real tools do it

Nginx starts a master process that opens the listening sockets, then forks N worker processes that all call accept on the same sockets (the kernel hands each connection to one of them). Postgres has a "postmaster" process in exactly today's loop; for each accepted connection it fork()s a child process that serves that one client for its whole life. Redis is a single process, single thread, that uses epoll to serve tens of thousands of connections in one loop. Three different answers to the one-at-a-time problem, all starting from today's seven syscalls.

What if it's missing?

If there is no backend at all

Any rule enforced only in the client is not enforced. Any data stored only in the client is one device loss from gone. Any secret shipped in the client is public. A "backend-less" product that needs any of the five reasons will be discovered either by a bug report ("my list disappeared when I got a new phone") or by an attacker ("I set the price to zero"). The failure is silent until it isn't.

If you build it wrong

  • Trusting the client. Taking the price, the user ID, or the "isAdmin" flag from the request body. The backend exists to be the thing that doesn't do this.
  • Keeping state in the process. Storing sessions or data in a global variable works with one server and breaks the moment you run two. Day 20 (stateless design) and Day 26 (12-factor) cover this.
  • Doing slow work inline. Sending an email inside the request handler means the user waits for the email provider. Day 12 moves that to a queue.
  • One client at a time in production. Today's design, shipped. It falls over at the second simultaneous user. Day 19 to 21.

If the usual pieces are not available

  • You cannot run a server (no budget, no ops). Use a static site plus a managed service for the one thing that needs a backend: an auth provider, a hosted database with row-level security, a serverless function. You still have a backend; you just rent it. Trade-off: vendor lock-in and per-request pricing versus zero operations.
  • The network is unreliable or absent (field apps, offline-first). Local-first design: the client keeps a full local copy and syncs when it can. The backend becomes a sync and conflict-resolution service rather than the only copy. Trade-off: conflict resolution is hard, and "trust" rules must be re-checked on sync.
  • No central server is acceptable (peer-to-peer, privacy). Each client is also a server: it runs today's accept loop. BitTorrent and some messaging apps work this way. Trade-off: you give up the single source of truth and must handle NAT traversal, discovery, and untrusted peers.
  • Only one machine, two processes (a CLI talking to a daemon). Same code, but AF_UNIX instead of AF_INET: a Unix domain socket at a filesystem path. No port, no handshake over IP, much faster, and the kernel can tell you the peer's user ID for free. Docker's CLI talks to its daemon this way.

Common mistakes & gotchas

  • "Address already in use" on restart. TCP keeps the old port in TIME_WAIT for about a minute. SO_REUSEADDR before bind fixes it. Every production server sets it.
  • Forgetting htons. The server silently listens on the wrong port. Always check with ss -ltnp or netstat.
  • Closing the listening socket instead of the connection socket. The server serves one request and then every accept fails. Keep the two fds clearly named.
  • Never closing the connection socket. Each request leaks one fd. After about 1024 requests, accept returns EMFILE and the server is dead while still "running". RAII makes this impossible; in C, discipline does.
  • Missing or wrong Content-Length. Too small and the browser truncates the page. Too large and it spins waiting for bytes that never come, until the close. Compute it from the actual body.
  • A recv buffer with no room for the NUL. sizeof buf - 1 in the C version is deliberate. Reading sizeof buf and then writing buf[n] = 0 is a one-byte overflow.
  • Backlog too small. Under a burst, the kernel refuses connections your process would have handled a millisecond later. Nginx uses 511; the kernel caps it at somaxconn.
  • Binding to 0.0.0.0 without meaning to. It exposes the port on every interface, including the public one. For a local tool, bind to 127.0.0.1.

Think about it

1. Start the server and run curl -v localhost:8080. Identify every line curl prints as either "bytes we sent" or "bytes we received".

Lines starting with > are the request curl sent (request line and headers). Lines with < are the response your server wrote. The * lines are curl's commentary (DNS, connect). What you see is exactly the content of buf and resp in the program.

2. What would happen if you removed the close(conn_fd) line?

The browser would wait for more data (we promised Connection: close but never closed), eventually render after its timeout, and your process would leak one fd per request. After roughly a thousand requests, accept fails with "Too many open files" forever. Nothing crashes; the server just stops serving.

3. What would happen if two copies of the server started on the same port?

The second bind fails with "Address already in use" and the program exits. SO_REUSEADDR does not allow two live listeners (that needs SO_REUSEPORT, which is how some servers run multiple accept loops on one port). The kernel enforces one listener per address:port.

4. Change the backlog to 1, add sleep(5) in the loop, and open five tabs at once. What do the later tabs see and why?

The first is served; one or two sit in the accept queue; the rest get connection resets or hang in their own retry. The kernel completed their handshakes but had nowhere to put them, so it dropped them. Your process never knew they existed. This is why "the server is up" and "the server is accepting connections" are different statements.

5. (Harder) Make the server return a different body for GET /time (the current time) and 404 Not Found for anything else. What did you have to parse, and what did you have to get right in the response?

You parsed the request line: method, path, version, separated by spaces. You had to send a different status line (HTTP/1.1 404 Not Found) and a correct Content-Length for each body. Congratulations, you have written a router (Day 4) and discovered why status codes exist (Day 3).

Quiz

1. What are the three things a client fundamentally cannot provide that a backend can?

A shared source of truth, trust (rules the user can't bypass), and capability (secrets, heavy work, access to other systems).

2. Who completes the TCP handshake on the server side, and when does your process learn about a new connection?

The kernel completes it on its own after listen(). Your process learns about it only when accept() returns the new fd.

3. Why can today's server handle only one client at a time?

Every call blocks. While it waits in recv or runs the handler for one client, it cannot call accept for the next one. Other clients wait in the kernel's accept queue.

4. A product has one user, one device, and no secrets. Should it have a backend?

No. None of the five reasons apply. Adding one brings cost, outages and attack surface for nothing. Add it when a reason appears.

5. What is the difference between the listening socket and the connection socket?

The listening socket is created once and only ever used with accept. Each accept returns a new connection socket that carries one client's bytes; it is closed when that client is done. Mixing them up kills the server.

Summary & key terms

A backend exists to be the one place the user cannot tamper with: it holds the single copy of the data, enforces the rules, and keeps the secrets. Mechanically it is a process that does socket, bind, listen once, then loops on accept, recv, work, send, close. The kernel does the handshakes and holds the buffers; the process only sees file descriptors. Because every call blocks, the simplest server handles one client at a time, which is the limit the rest of the course spends several days removing. The browser understands the reply because the protocol, not the language, is the contract.

TermMeaning
BackendA process you control, reachable over a network, that owns the truth.
Trust boundaryThe line between code you control (server) and code the user controls (client). Nothing crossing it inward is trusted.
Listening socketA socket after bind + listen. Used only to accept. Never read from or written to.
Accept queue / backlogThe kernel's queue of handshake-completed connections waiting for accept. Its length is the argument to listen.
Connection socketThe fd returned by accept, representing one client. Read, write, then close.
Blocking callA syscall that puts the process to sleep until the kernel has a result. Efficient, but serializes work.
SO_REUSEADDRSocket option that lets you re-bind a port still in TIME_WAIT. Set it before bind.
TIME_WAITTCP state where a closed connection's port is held briefly so late packets don't hit a new connection.
Network byte orderBig-endian, used for ports and addresses on the wire. htons/htonl convert to it.
Unix domain socketA socket addressed by a filesystem path, for processes on one machine. Same API, no IP or TCP.
Local-firstDesign where each client keeps a full copy and syncs; the backend resolves conflicts instead of being the only copy.
